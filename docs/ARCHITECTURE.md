# Architecture

## System diagram

```text
┌────────────────────────────── Tauri window ──────────────────────────────┐
│  Svelte 5 UI                                                             │
│    routes/  components/  stores/                                         │
│       │  invoke()                         ▲  listen("chat://delta", …)   │
│       ▼                                  │                               │
│  src-tauri: IPC commands + event forwarder                               │
│       │                                  │                               │
│       ▼                                  │                               │
│  tnn-core (AppCore)                                                      │
│    catalog ─ hardware ─ storage ─ downloads ─ engine supervisor ─ chat   │
│       │                        │                 │              │        │
│       ▼                        ▼                 ▼              ▼        │
│  SQLite (app data)     <file>.part → model    llama-server    SSE parser  │
│                                               127.0.0.1:random           │
└──────────────────────────────────────────────────────────────────────────┘
```

The engine is a sidecar process, never a library. Rust owns its lifetime and is
the only process that talks to it. The webview has no socket to the engine.

## Crates

### `crates/tnn-core`

UI-independent domain. This is where all behaviour and tests live.

| Module | Responsibility |
|---|---|
| `app.rs` | `AppCore` orchestration: bootstrap, model actions, chat, benchmark, shutdown |
| `hardware.rs` | CPU feature detection, RAM, minimum mode, tier selection, recommendations |
| `paths.rs` | Single app-data layout; engine dirs come from Tauri resources |
| `errors.rs` | `AppError` → stable code, message, recovery actions, retryability |
| `events.rs` | Transport-neutral `CoreEvent`, payloads and `EventSink` |
| `models/catalog.rs` | Embedded catalogue, recommendation, downloadability rules |
| `models/download.rs` | Resumable HTTP download, SHA-256, GGUF gate, atomic install |
| `models/verify.rs` | URL host allowlist, hashing, disk space, model-id validation |
| `models/gguf.rs` | Header parsing for install/import validation |
| `models/install.rs` | Atomic rename, unique names, safe import copy |
| `engine/args.rs` | The exact llama-server command line (loopback, no UI, no GPU) |
| `engine/manager.rs` | Spawn, health, self-test, fallback, chat, benchmark, stop |
| `engine/health.rs` | `/health` polling, 200-line log tail, crash classification |
| `engine/lifecycle.rs` | Process groups, executable bits, priority, PID file cleanup |
| `engine/selftest.rs` | Tiny completion before declaring the engine ready |
| `engine/stream.rs` | SSE client, 50 ms delta batching, cancellation |
| `chat/context.rs` | Token estimate and context truncation |
| `chat/sse.rs` | Incremental SSE parser (UTF-8-safe, multi-line data, `[DONE]`) |
| `storage/` | Migrations, typed DB access, settings validation and patches |
| `diagnostics.rs` | Redacted diagnostics bundle and logs |

### `crates/mock-engine`

Deterministic fake `llama-server` used by tests and local UI development. It
accepts the real flags, enforces the bearer key, serves `/health`, `/props`,
`/tokenize` and OpenAI-compatible SSE. Fault modes:
`MOCK_ENGINE_BEHAVIOR=normal|garbage|hang|crash|slow`.

### `src-tauri`

Thin adapter:

- registers single-instance, window-state, dialog, opener, clipboard, process
  and updater plugins (no shell plugin);
- resolves `resources/engine` and `resources/engine-baseline`;
- sets up rotating logs and forwards `CoreEvent` to webview events;
- runs the idle-unload monitor and terminates the engine on exit;
- exposes the commands listed below.

### `src`

Svelte 5 runes UI. `src/lib/tauri.ts` is the only module that calls `invoke`.
`src/lib/bindings` is generated by `ts-rs`; do not edit it by hand.

## IPC commands

```text
get_bootstrap_state        list_models                get_settings
scan_hardware              download_model             update_settings
get_storage_summary        pause_download             run_benchmark
start_engine               resume_download            export_diagnostics
stop_engine                cancel_download            open_data_dir
engine_status              delete_model               open_logs
send_message               import_model               check_for_updates
cancel_generation          list_conversations
regenerate                 get_conversation
continue_response
create_conversation        rename_conversation
delete_conversation        export_conversation
```

All commands return `Result<T, ErrorPayload>`, serialized as
`{ code, message, detail, recovery, retryable }`.

## Events

| Event | Payload |
|---|---|
| `download://progress` | `{ model_id, bytes_done, bytes_total, speed_bps, eta_secs? }` |
| `download://state` | `{ model_id, state, error? }` |
| `engine://state` | `{ state, model_id?, tier?, compatibility_mode, error? }` |
| `chat://delta` | `{ request_id, delta, reasoning_delta?, index }` |
| `chat://done` | `{ request_id, usage, elapsed_ms, tokens_per_sec }` |
| `chat://error` | `{ request_id, error }` |
| `chat://cancelled` | `{ request_id }` |
| `benchmark://progress` | `{ model_id, stage, percent }` |
| `update://available` | `{ version, notes? }` |

Events carry payloads only; the Tauri layer adds the event name. Deltas are
batched every 50 ms to keep a 2-core machine responsive.

## Data flow: send a message

1. UI optimistically appends the user message and a streaming assistant
   placeholder, then calls `send_message`.
2. `AppCore` verifies the model is installed, builds a truncated context with a
   reserve for the answer, and registers a cancellation token under
   `request_id`.
3. `EngineManager::ensure` starts the engine if needed (health + self-test),
   then `stream_chat` posts the OpenAI-compatible request with the session key.
4. The SSE parser accumulates content/reasoning and emits `chat://delta`
   every 50 ms. The full answer is persisted when the stream ends.
5. Cancellation stops reading and persists the partial answer as
   `interrupted`. It is not an error.
6. `chat://done` reports usage and speed; the UI replaces the placeholder with
   the persisted message.

The SSE proxy retains the engine's `finish_reason`. A `length` finish or an
unexpected EOF saves the answer as `truncated`, which is distinct from
`complete`. The UI preserves and renders that text and offers **Continue
answer**. `continue_response(conversation_id, request_id)` validates both IDs
and the latest assistant turn, then uses that message as an assistant prefill
(`continue_final_message: true`, `add_generation_prompt: false`, `echo: false`).
Only newly generated text is streamed and appended to the same stored message;
no synthetic user message is persisted. Existing answers and manually stopped
answers can also be continued. The context and output budgets still apply;
continuation fails visibly if the existing answer no longer fits context.
While the engine processes the existing answer, the UI shows a preparation
message. HTTP requests can be cancelled before response headers arrive.
Prompt processing has no automatic deadline: baseline CPUs may need many
minutes before the first token. After the first content or reasoning token,
a 180-second gap without further output ends with a recoverable engine error.
This is an inactivity limit, not a limit on total response time; SSE
keep-alives do not reset it. Stop remains available during prompt processing.

## Storage

SQLite at `<app-data>/tnn.sqlite3`, migrations applied in order at startup
(`user_version`). Tables: `conversations`, `messages`, `installed_models`,
`downloads`, `settings`, `benchmarks`. Foreign keys cascade messages when a
conversation is deleted. Partial downloads live in `downloads/<name>.part`;
only verified files are moved into `models/` atomically.

## Paths

```text
<app-data>/                 database, pid file
<app-data>/models/          verified GGUF files
<app-data>/downloads/       resumable .part files
<app-data>/logs/            rotating app/engine logs
<app-data>/exports/         conversation exports and diagnostics
<resources>/engine/         pinned engine payload
<resources>/engine-baseline/ SSE2 x64-only fallback
```

## Security boundaries

- `127.0.0.1` + random port + random per-session key + `--no-ui`.
- CSP: self-only scripts/styles/images, no remote origins, `object-src 'none'`,
  `frame-ancestors 'none'`.
- Tauri capabilities: core defaults plus dialog, opener, clipboard, updater,
  process-restart and window-state. No shell, no broad FS plugin.
- Model URLs: HTTPS only, host allowlist, redirects re-checked, pinned SHA-256.
- Markdown: DOMPurify profile that forbids active content; links go through
  `openExternal()` which accepts only `http`/`https`.
- Logs: API keys are never logged; prompts and paths are excluded from
  diagnostics by default.
